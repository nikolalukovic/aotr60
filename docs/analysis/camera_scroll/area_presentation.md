# AREA presentation

## SUMMARY

AotR60's camera presentation does not cause the slowdown and does not make it worse. On a slope the A-only, stock-stepped camera never trips a cut rule. The halfway/M_k presentation gives exactly the stock 30 Hz speed profile, split into two equal half-steps and shown 16.7 ms later. The slowdown comes from stock W3DView behaviour, so it should look the same at stock 30 FPS. (1) The eye's absolute height is zoom*offset.z and does not follow the terrain. (2) Height settling is switched off while scrolling fast (ScrollAmountCutoff 50, EnforceMaxCameraHeight=No) unless the height above ground drops below the minimum (120). (3) scrollBy moves the camera a world distance proportional to zoom (absolute height), not to height above ground. So the on-screen pan speed goes as Z/(Z - g). Descending 200 units from a settled height of 300 slows the pan to 0.60x. Climbing speeds it up (up to about 2.6x) until the height drops below 120. Then the camera jumps up 30 % of the gap in one frame, and that sudden zoom-out reads as braking. Telemetry from the latest session backs this up: 6 cuts in 2454 interpolated A-frames, none during the sustained pans; 0 shake-paused; 1 no-history; 0 guard-ends. Split present and the pacer cause hitches in battle (a frame held over 25 ms about 5 times a second), but these follow logic load, not terrain height.

## STOCK

Yes, and it should be the same at stock 30 FPS. This is INFERRED from the code plus a model; the user has not run an in-game A/B yet. The mechanism is all stock code in W3DView. (1) The eye height is absolute: builder 0x502858 uses eye.z = offZ*zoom with factor 1 - ground/(offZ*zoom) at 0x502B65. (2) scrollBy 0x48C774 moves the camera |delta| * zoom * 0.25 * scrollScalar world units per A-frame, which scales with absolute height rather than height above ground. (3) While |scrollAmount| >= ScrollAmountCutoff (50 in AotR), the height settle 0x48C35D is suppressed unless height above ground falls below DefaultCameraMinHeight 120, because EnforceMaxCameraHeight = No. The result: descending into lower terrain while panning raises the height above ground at a fixed eye height. A 200-unit drop from a settled 300 slows the on-screen pan to 0.60x. Climbing speeds the pan up until the height above ground goes under 120. Then the camera pulls up by 30 % of the gap in one 33 ms frame, a sudden zoom-out that reads as braking. When the scroll slows below the cutoff or stops, the camera re-settles over about 280 ms. To confirm in game: pan the same slope with Ctrl+Shift+F11 (stock 30) and with Ctrl+Shift+F10 (smoothing off). The speed change should be identical; only the smoothness and the 16.7 ms delay should differ.

## AOTR60

None that changes speed. 60 mode runs every camera integrator (height settle, min-height snap, scroll) once per A-render at the stock cadence; there are no patches in 0x48BD25..0x48C700, and InGameUI and translator scroll are A-only. The presentation shows each 30 Hz step as two equal half-steps: A = halfway(M_{k-1}, M_k), B = M_k. Pair displacement equals stock exactly, so the speed profile is stock's with a constant 16.7 ms delay. A snap that stock shows as one 56-unit jump is shown as 28 + 28, which is smoother. Slopes cannot trip the cut rules because near (10), far (GD+0x950 * 1800) and hfov (view+0x6C) do not change with height or terrain (0x48B816..0x48B909). Telemetry agrees: 6 cuts in 2454 interpolated A-frames, 0 during the sustained pans at t = 42-53 s and t = 296 s. Units and the C4 cache use the same half-step delay as the camera, and terrain is static, so nothing can move at a different speed from the camera. Split present and the pacer add battle-load hitches (a frame held over 25 ms up to about 5.8 times a second after t = 254 s), but these do not depend on elevation.

## FIX

No AotR60 fix is needed for the elevation slowdown. AotR60 is presentation-only and stock-exact, and it neither causes nor amplifies the effect. If the user wants panning that feels terrain-independent, this has to be a deliberate change to stock camera behaviour, made in both modes. Options: (1) Data-only: in AotR gamedata.ini set EnforceMaxCameraHeight = Yes, so the settle also fires when height above ground exceeds the max (300) while scrolling. Optionally raise ScrollAmountCutoff so the camera follows the terrain during scrolling with the 0.3/frame lag. Check whether INI changes affect multiplayer CRC before shipping. (2) Optional DLL feature (off by default, client-only): scale the scrollBy world step at 0x48C959 (fld [ebx+0x3C] zoom) by HAG/HAGd, using view+0x50 (current height above ground) and view+0x40 (desired height above ground), so the on-screen speed stays constant. Camera position is client state, but this still has to be checked against the logic-side camera readers listed in ../gaps/G2_drawpath.md. Separately, track the battle-phase hitches (holds_over25 at about 10 % of frames after t = 254 s) as a pacing / split-present item, since they make pans look uneven during heavy logic whatever the terrain. Scratch files: <analysis workspace>/camera_elev\presentation\sim.py, build_502858.c, vt5c.txt, aotr60.log, aotr60_rates.csv (copies).

## FINDING [confirmed] Clip planes and view plane do not change with camera height or terrain, so slopes cannot trigger the cut rules
setCameraTransform 0x48B7B1 sets clip planes at 0x48B837 with near = [0xBD83D8] = 10.0 and far = GD+0x950 * [0xBDD730] (1800.0). Both are per-game constants and do not depend on zoom or terrain. The view plane is set at 0x48B909 from hfov = view+0x6C (vfov -1, so the aspect is derived), or from GD+0xEA8 in panorama mode, and at 0x48B93D only in mode 4. view+0x6C is written only by event-driven code: 0x4866A7, 0x486F76, 0x48713E, 0x48A72D (object/cinematic camera) and 0x48CB99. Nothing writes it per frame from height. So vp[4..6] are bit-identical between A-renders and vp[0..3] stay constant. The only cut that can fire is the eye-translation limit (>1500 units in 33 ms) or the 45 deg rotation limit, and neither happens during a normal pan. My 1-D model of a 200-unit ramp gives at most 40-73 units of eye travel per A-frame and 56 units of vertical travel on the settle frame.
EVIDENCE: Disassembly 0x48B816..0x48B93D. Constants read from the binary: 0xBD83D8 = 10.0, 0xBDD730 = 1800.0. Writers of [view+0x6C] found by searching listing.asm. Session telemetry (aotr60_rates.csv, cumulative): cam_a_cuts = 6 against cam_a_swaps = 2454 (0.24 %). The two sustained-pan windows at t = 42.0 and 52.6 s added 306 and 308 A-swaps (about 96 % of A-renders) with cuts flat at 1. The window at t = 296 s added 210 swaps and 0 cuts. New cuts appear only in isolated windows (253.9, 307.0, 338.7 x2, 370.4), which fits minimap or selection jumps. Final telemetry line: cuts 6, shake-paused 0, guard-ends 0, no-record 0. no-history = 1, at the mode switch.
IMPLICATION: Hypothesis (a) is ruled out. During a pan over changing elevation the picture never falls back to 30 Hz steps.

## FINDING [confirmed] Halfway presentation keeps the stock speed profile exactly (constant 16.7 ms delay, no lag or lead that depends on elevation)
Every camera integrator, including the height settle 0x48C35D..0x48C399 (zoom += (desired - zoom) * CameraAdjustSpeed 0.3) and the min-height snap, runs only in the A-render's stock W3DView::update. sites.json has no patch inside 0x48BD25..0x48C700 apart from S1/S2, and there is no settle-constant redirect. Keyboard scroll (InGameUI::update 0x6A23CA, gate GATE_GC_IGUI) and translator scroll (0x83B8A4, during propagate, empty on B) also run only on A, so scrollBy 0x48C774 is called at the stock cadence of once per A-render. Presentation shows A_k = halfway(M_{k-1}, M_k) and B_k = M_k. Each 30 Hz step therefore appears as two equal half-steps, and the displacement over a pair equals stock's exactly. In the model, max |pair displacement - stock displacement| = 0. A settle snap that stock shows as one 56-unit jump appears in 60 mode as 28 + 28, which is smoother, not slower. The 'camera did not move' early-out only triggers when M_{k-1} == M_k bit for bit, which never happens during a pan. The shake hold does not apply (aShake 0, shake-held 47 from impacts).
EVIDENCE: src/camera.cpp: SceneOpen_A (r1.renderId == g_renderId, r0 == g_renderId - 2, memcmp no-move check), CamSwapToMk_B, S2_RecordMkAndOpen. src/camera_math.cpp InterpolateCameraHalfway: translation and extents averaged, rotation via slerp(1/2) as a normalised sum. tools/sites.json has 148 sites and none in the settle/scroll code. <analysis workspace>/camera_elev/presentation/sim.py (not in the repo) prints for 'down' a stock speed of 1.00 -> 0.60, the 60-mode profile identical, and pair displacement error 0.
IMPLICATION: Hypothesis (b) is ruled out. AotR60 adds a fixed 16.7 ms delay to the camera and to the units equally, and introduces no change in speed with elevation.

## FINDING [confirmed] Stock cause, part 1: eye height is absolute (zoom * offset.z) and the scroll step is proportional to zoom, not to height above ground
In the camera builder 0x502858, factor = 1.0 - ground/(offZ*zoom) at 0x502B45..0x502B6B (fsubr qword [0xBD2C98] = 1.0). The eye is then pivot + R*offset*zoom*factor with eye.z = ground + offZ*zoom*factor, which equals offZ*zoom. The pivot ground level view+0x2408 is updated only while scrolling (0x48C1F6..0x48C236, capped at 5000). scrollBy 0x48C774 moves pos by |delta| * zoom(view+0x3C) * 0.25([0xBD1904]) * scalar. The scalar comes from settings-object vt+0x10 = 0x9E68DC, which returns +0x14 (DefaultCameraScrollSpeedScalar 1.0). The world step therefore depends on absolute camera height, not on distance to the ground, and on-screen ground speed goes as zoom/(Z - g) = Z/HAG.
EVIDENCE: Disassembly 0x502B45..0x502B79 and 0x48C936..0x48C970. Settings vtable 0xBE5648: slot 0 = 0x5F2D3D (+4, min height), slot 1 = 0x5F2D41 (+8, max height), slot 4 = 0x9E68DC (+0x14, scroll scalar). Keyboard scroll delta per A-frame uses the constant [0xDA0B24] = 250.0 (0x6A2291), so it is frame-based.
IMPLICATION: Over lower ground the camera is farther away while the world step stays the same, so the pan looks slower. Over higher ground it looks faster. This happens identically at 30 FPS.

## FINDING [likely] Stock cause, part 2: height settle is off during fast scrolls except below the minimum height, and that rule produces a one-frame zoom-out when climbing
W3DView::update B5 runs 0x48C2F3..0x48C399 only while InGameUI vt+0xA8 (isScrolling) is set. If |scrollAmount| (view+0x23FC) < cutoff (view+0x2404; ScrollAmountCutoff = 50 in AotR gamedata.ini), it settles. Otherwise it settles only if HAG < min (+4; DefaultCameraMinHeight 120) or if GD+0xAB4 (EnforceMaxCameraHeight = No in AotR) is set and HAG > max. The settle is zoom += 0.3*(desiredZoom - zoom) with desiredZoom = (view+0x40 + terrain view+0x54)/offZ. In the model (HAGd 300, 200-unit ramp, fast scroll): descending gives relative screen speed 1.00 -> 0.92 -> ... -> 0.60 over about 0.4 s and it stays at 0.60 until the scroll slows. Climbing gives 1.0 -> 2.65 as HAG drops toward 120, then the snap raises the eye about 56 units in a single 33 ms frame. That is a sudden zoom-out with screen speed 2.65 -> 2.28, which reads as braking. When the scroll drops below the cutoff or stops, the camera settles back to HAGd with time constant 0.3 per A-frame (about 95 % in 280 ms), which changes the apparent speed again.
EVIDENCE: Disassembly 0x48C186..0x48C497. gamedata.ini lines 11253-11276 (DefaultCameraMinHeight 120, DefaultCameraMaxHeight 300, CameraAdjustSpeed 0.3, ScrollAmountCutoff 50, EnforceMaxCameraHeight No). <analysis workspace>/camera_elev/presentation/sim.py profiles. The numbers are model values; the user's actual HAGd and terrain deltas are unknown.
IMPLICATION: This explains a pan that slows when going down and brakes when going up, in both modes. AotR60 runs this code unchanged at the stock 30 Hz cadence.

## FINDING [confirmed] Unit presentation fraction and C4 transform cache are consistent with the camera presentation
On A-renders, units use fraction (2k-1)/12 with key 2*m_frame-1, and the camera shows halfway(M_{k-1}, M_k). On B-renders it is fraction k/6 with camera M_k. Both run half a step behind, so units and camera share the same 16.7 ms delay. Terrain is static geometry and therefore moves on screen exactly with the presented camera. The A-render drawable pass and terrain re-centre use the real camera C_k, which matters only for culling and window edges and has no effect on speed.
EVIDENCE: PLAN 1.2/1.6. camera.cpp OpenWindow (g_presFrac in the presentation windows). S2 at 0x48C701 records M_k before the pass.
IMPLICATION: Hypothesis (c) is ruled out. Terrain and units cannot appear to move at a different speed from the camera.

## FINDING [likely] Split present and the pacer cause battle-load hitches, not elevation-dependent slowdown
In this session the frame-pacing quality drops in the battle phase, not with terrain. holds_over25 (Present spacing over 25 ms, i.e. a 3-vblank frame at 120 Hz followed by a short one) runs at 0-2 per 10.6 s window up to t = 243 s, then 36-62 per window from t = 254 s (up to about 5.8/s, roughly 10 % of frames). on_time_pct is 90-92 % and late_releases 50-62 per window. While panning, a 25/8 ms display pair looks like a momentary stall and catch-up. Game-time loss (debt) is at most 196 ms per 10.6 s window (under 1.9 %), and the scroll step is frame-based in both modes, so it is not a perceptible sustained slowdown. Nothing in split present or the pacer reads camera height or terrain.
EVIDENCE: aotr60_rates.csv columns holds_over25, holds_over34, on_time_pct, late_releases, debt_ms. The log's split-present summary reports 'holds over 25 ms 70' by t = 147 s. Spikes in logic1_max/logic_other_max (up to 185 ms) line up with the late frames.
IMPLICATION: Hypothesis (d) is unrelated to elevation. Battle-time judder is a separate pacing item, and the telemetry already tracks it.

## VERIFIER
The analysis is mostly right about AotR60's camera presentation. It is wrong or unproven in four places: its causal story, the telemetry numbers it quotes, its account of the "going up" half of the report, and both proposed fixes.

CONFIRMED from the binary and the repo:
- The height settle, the min-height snap and scrollBy run only inside the stock W3DView::update / InGameUI / translator code, which runs on A-renders. tools/sites.json has only S1 0x48BD1B, S2 0x48C701 and S2E 0x48C765 anywhere in 0x48BCF2..0x48CA80, 0x502858.., 0x6A2200.. and 0x83B500..
- scrollBy moves |delta| * zoom(view+0x3C) * 0.25 * scalar (0x48C959..0x48C9AC; scalar from settings +0x14 via 0x9E68DC).
- The eye is at an absolute height Z = offZ * zoom (0x502B45..0x502B6B, factor = 1 - g/(offZ*zoom)).
- Settle rules 0x48C2F3..0x48C399: cutoff from GD+0xAAC copied to view+0x2404 at 0x48BCC9, min height from settings vt0, max height only if GD+0xAB4, rate GD+0xAB0. The GD offsets map through the INI field table to ScrollAmountCutoff, EnforceMaxCameraHeight and CameraAdjustSpeed.
- near = 10, far = GD+0x950 * 1800, hfov from view+0x6C (0x48B816..0x48B909).
- The A = halfway, B = M_k presentation splits each 30 Hz step into two exactly equal halves (my model: 9e-13 units difference). It adds a constant 16.7 ms delay and no speed change.
- Cuts 6 of 2454 A-swaps, with none in the pan windows at t = 42 / 52.6 / 296.3. shake-held 47, shake-paused 0, guard-ends 0, no-history 1.

The analysis did not check the premise that settling is off while scrolling; I checked it. With Options.ini ScrollFactor = 50, 0x641E0C..0x641E1F sets GD+0xA9C = GD+0xAA0 = 1.0. That gives keyboard |delta| = 250 (0x6A22AE), edge scroll up to 100 after the 0.25 s ramp (0x83B515..0x83B6EF), and RMB drag about 1 per pixel. All of these are at or above the cutoff of 50 almost all the time.

WRONG or UNPROVEN:
1. Causal story. My model reproduces the analysis's numbers: 0.60x going down, 2.65x then 2.28x going up, a 56-unit snap. But the slowdown is mostly a steady state, not a transient from suppressed settling. scrollBy scales with zoom, and zoom carries the absolute ground height ((HAGd + g) / offZ). So once the camera has settled, screen and world pan speed are (HAGd + g) / HAGd. With settling forced on (|delta| = 40) the descent still ends at 0.60 and the climb at 1.67. The slowdown over low ground is permanent for that height, not something that recovers in about 280 ms.
2. "Going up slows down" is not explained. The model predicts that climbing speeds the pan up (2.3x, or 1.67x once settled). The min-height snap is a 14 % dip inside that speed-up. Calling it "reads as braking" is a guess.
3. Telemetry numbers misquoted. The figures "holds_over25 0-2 per window until t = 243 s, then 36-62 (5.8/s)" are actually the late_releases column. Real holds_over25 is 19 / 8 / 15 / 18 in the pan-heavy windows at t = 31.3 / 42.0 / 63.2 / 296.3. "Debt at most 196 ms" is wrong: it is 413.9 ms at t = 31.3. "on_time 90-92 %" only holds after t ≈ 285 s.
4. Both fixes miss the main cause. EnforceMaxCameraHeight = Yes and a wider cutoff still end at 0.60x (model). Scaling the step by HAG/HAGd still leaves screen speed proportional to Z/HAGd = (HAGd + g)/HAGd. The step would need to scale with eye-to-pivot distance, i.e. HAG/offZ = zoom - g/offZ, instead of zoom. That is a stock-feel change and needs a reference height.

Minor issues:
- The hfov writer list is partly wrong. It omits the virtual setter 0x485AC5, and the 0x48CB99 entry is really fn 0x48D26B at 0x48D388.
- Min and max height can be overridden per map through the world-dict keys cameraMinHeight / cameraMaxHeight (0x50136C / 0x5013A6). 120 / 300 are only the defaults.
- The terrain height g comes from a separate bilinear camera-height grid (0x70FE22 on view+0x2458) when the map has one. Only that path updates the pivot plane view+0x2408. Otherwise it comes from 0x484FAB (max of samples at ±CameraTerrainSampleRadiusForHeight 1.0).
- "Stock 30 FPS looks identical" is still INFERRED. Nobody has tested it in game.

## MISSED
1. The main stock mechanism is the steady state, not the cutoff. The scroll world step is |delta| * zoom * 0.25 (0x48C959), and zoom = (HAGd + g)/offZ. So both pan speeds, on screen and across the map, go as (HAGd + g)/HAGd: 1.33x per 100 units of ground height at HAGd 300. Panning from high ground onto low ground slows by 0.60x and stays that way after settling.

2. "Going up slows down" is still unexplained by stock code. Climbing speeds the pan up. Candidates the analysis did not test:
- repeated min-height snaps on long, steep climbs, which make a stepwise zoom-out stutter;
- the slow side of the same hill, i.e. the descent after a climb;
- render hitches, see point 3.
The user's phrase may also mean screen-up/down scroll direction. Ask the user.

3. Render-side hitches correlate with panning, which the analysis did not mention.
- A-render stalls of 25-163 ms with no logic time are 3.9 per window when the camera moves, against 1.3 per window when it does not.
- holds_over25 peaks in the pan windows.
- Debt is 414 ms and 153 ms in the first pan windows.
Scroll advances by a fixed step per A-render (no time scaling), so each stall stops the camera for its length and then the camera continues. This reads as a slowdown. A zoomed-out camera over low ground (HAG up to 500) also shows more terrain and objects, which plausibly raises render cost. Unproven; check stall timestamps against pans in a test.

4. Per-map overrides and height sources.
- cameraMinHeight, cameraMaxHeight and cameraScrollSpeedScalar can come from the map's world dict (0x50136C..0x501454), so 120 / 300 / 1.0 are only defaults.
- g comes from a map camera-height grid (0x70FE22, bilinear, view+0x2458, flag view+0x2474) when the map has one. Only that path updates the pivot plane view+0x2408 while scrolling (0x48C1F6..0x48C236).
- Otherwise g comes from 0x484FAB, a max of samples within CameraTerrainSampleRadiusForHeight = 1.0, i.e. effectively a point sample.

5. Input regime at ScrollFactor = 50.
- Options.ini ScrollFactor = 50 sets HorizontalScrollSpeedFactor = VerticalScrollSpeedFactor = 1.0 (0x641E0C), overriding the INI's 0.4 / 0.5.
- Edge scroll ramps over ScreenEdgeScrollRampTime 0.25 s (0x83B515..0x83B53C). For roughly the first 125 ms, |delta| is below 50 and settling is active.

6. Suggested in-game checks:
- Pan from high ground to low ground and back at stock 30 (Ctrl+Shift+F11) and with smoothing off (Ctrl+Shift+F10).
- Note whether the slowdown persists after stopping and restarting the scroll. The steady-state mechanism predicts it does; the transient explanation predicts it does not.
- Watch for hitches (stall lines in aotr60.log) at the same moments.
